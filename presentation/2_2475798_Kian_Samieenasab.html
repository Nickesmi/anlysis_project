3. What to say

Now that every sentence is a list of word ids, we need a rule for when two sentences match. The task says a copy can have small edits: a word added, removed, replaced, or two neighbouring words swapped. So we use the optimal string alignment distance on words, OSA for short. It is the smallest number of those four edits that turns one sentence into the other. We chose it over normal Levenshtein because Levenshtein counts a swap as two edits, and over word-set measures like Jaccard because those do not see a swap at all.

Two sentences match if the distance is at most 30% of the longer sentence, rounded down. So a sentence of three words or less has to be identical, a 10-word sentence can have 3 edits, and a 23-word sentence can have 6. We started with 25%, but in our generated tests 30% found three more heavily edited short sentences and still gave zero false matches. In the sample documents no two different sentences are even within 40% of each other.

The distance is a dynamic programming table. Cell i, j is the distance between the first i words of one sentence and the first j words of the other. It takes the minimum of delete, insert, keep or replace, and the swap case, which looks two rows and two columns back. We only keep three rows in memory. The brute force does this for every main sentence, every document and every sentence in it, so it is O(n times S times w squared). On 200 documents that is 600 000 full tables. Nikan will show how we avoid almost all of them.

6. Questions you will probably get

Why OSA and not Levenshtein?
The task lists a swap of two neighbouring words as one small edit. Levenshtein would need a delete and an insert (or two replacements) for it, so a sentence with two swaps would look like four edits. OSA counts each swap as one.
Why compare words and not characters?
The edits in the task are word edits. Word sequences are also about 6 times shorter than character sequences, so the table is about 36 times smaller.
Why 30%?
We tested 25% and 30% on generated sets. 30% found three more sentences with 3 edits in short sentences and still had zero false matches. We also checked all pairs of different sentences in the sample documents: none are within 40% of each other, so 30% leaves a safe margin.
Why must very short sentences be identical?
floor(0.3 times 3) is 0. For a 3-word sentence one edit is a third of the sentence, and short sentences like "It is so." would match many unrelated sentences.
What is the time and memory of one OSA?
Time O(|a| times |b|), memory O(|b|) because we keep three rows: the current one, the previous one, and the one before it for swaps.
Is OSA a metric?
Not exactly, it can break the triangle inequality, unlike full Damerau-Levenshtein. We never need the triangle inequality, we only compare one pair at a time with a threshold, so it does not matter.
What if a main sentence matches two sentences in the same document?
It still counts once for that document, because the rate counts main_doc sentences. We keep the closest pair; if two are equally close we keep the earlier one.
Show the brute-force complexity.
n main sentences times S document sentences pairs, each a w by w table: O(n times S times w squared). With 200 documents that is 30 times 20 000 = 600 000 tables.
Give an example of a sentence you miss.
"In invaded canals solicitude intense pervaded the nation." against "In that crisis intense solicitude pervaded the nation.": 3 edits in 8 words is 37.5%, more than 30%. Almost half the sentence changed, so we would not call it a small edit.

Shared part: the whole project on one page (everyone must know this)

Pipeline

  1. Read main_doc.txt and documents/*.txt from the current folder (or --dir). Natural file order.
  2. Split into sentences (generator rule: no split after Mr./St./single capitals, not after a closing quote; empty line ends a sentence).
  3. Words to ids: lower-case, letters and digits, inner ' and - kept; our FNV-1a hash table with linear probing gives each word an int id.
  4. Match: OSA distance on words (insert, delete, replace, swap neighbours), match if distance <= floor(0.3 x longer length). Brute force: every pair, full DP. Efficient: main_doc index, pigeonhole skip, k+1 rarest words, length filter, bag-of-words filter, banded DP.
  5. Output: rate = matched main sentences / all main sentences; documents sorted by rate, ties in file order; up to 5 most similar pairs, edits listed.

Complexity in one line each

  • n main sentences, m documents, s sentences per document, S = m·s, w words per sentence, C characters.
  • Preprocessing: O(C) expected (both versions).
  • Brute force: O(n·S·w²).
  • Efficient: O(C + n·w log w + S·(w log w + n·w) + D·w²); worst case O(n·S·w²) if every pair survives; in practice D = real matches, so about linear.
  • Memory: O(C + V + n·w + m·n).

Numbers everyone should remember

  • Sample: 20/20 found (13 exact, 7 edited), same ranking and rates as expected_output.txt, 0 false matches.
  • 200 documents: 741 ms vs 14 ms (53x) with n = 30; 7.8 s vs 82 ms (96x) with n = 230; whole program 7.96 s vs 0.14 s.
  • Filters on 200 documents: 20 000 sentences, 6 670 skipped at once, 47 440 candidates, 200 DPs = 200 matches (brute: 600 000 DPs).
  • Generated tests: 800/800 (at least 10 words), 798/800 (at least 6 words), 0 false matches.

Questions anyone can get

Which files does it read and how do you run it?
main_doc.txt and documents/*.txt in the folder it is started from. Compile with g++ -std=c++17 -O2 -o plagiarism src/*.cpp, run with ./plagiarism (efficient), brute, compare, benchmark.
Did you use any built-in search?
No find, indexOf or regex in the core. Splitting, tokenizing, hashing and matching are our own code. We use standard containers (vector, sort), which the assignment allows.
Are the brute force and the efficient version really the same?
Same matching rule, and the efficient filters can only reject pairs that cannot match, so the result tables are identical. compare and benchmark check it every run.
What would you improve?
Reading the files is now the slowest part (about 48 ms for 200 documents); it could be done with memory-mapped files or in parallel. We could also make the threshold depend on the sentence length more carefully for very short sentences.
Did you use AI?
Yes, Claude, as written in our AI Use Declaration. We tested everything ourselves and each of us can explain all of the code.
