3. What to say

Hi, we are Nikan, Pouya, Kian and Mustafa. Our program gets a main document and a folder of documents, and for every document it tells you what percentage of the main document's sentences were copied from it, exactly or with small edits. The similarity rate is matched sentences of main_doc divided by all sentences of main_doc. The output is one block per document, most similar first, with up to five sentence pairs.

I will talk about the first step, turning the text into something we can compare fast. First we split the text into sentences. This sounds easy, but it decides the sentence count, so it changes every percentage. We noticed that every paragraph in the sample documents has exactly six sentences, so they were built from the generator's own sentences. We tried different rules, and only one gives six sentences in all 320 paragraphs: split at a full stop, question mark or exclamation mark followed by a capital letter, but not after Mr., St. or a single capital letter like in U.S., and not when a closing quote comes right after the full stop. A simple split on every ". " was wrong in eleven paragraphs.

Then we split each sentence into words, lower-case them, and give each word an integer id. For that we wrote our own hash table: the FNV-1a hash, open addressing with linear probing, and the table doubles when it is half full, so a lookup is O(1) on average. After this, a sentence is just a vector of ints, and comparing two words is one integer comparison. This step is O(C) for C characters, and it is the same for both versions. Kian will now explain when two sentences count as a match.

6. Questions you will probably get

Why didn't you use regex or string find?
The assignment does not allow built-in text search for the core task. We scan the text character by character, which is also O(C), so we do not lose anything.
How did you decide the sentence splitting rule?
From the data. Every paragraph of the sample documents has exactly six sentences, so the generator built the documents from its own sentence list. We tried several rules and only ours gives 6 in all 320 paragraphs. If our split differs from the generator's, a copied sentence can be cut in two and the sentence count changes, so the percentages would be off.
What happens with "U.S. Army"?
At the first '.' the next character is 'S', not whitespace, so it is not a boundary. At the second '.' the word before it is the single capital 'S', which we treat as an abbreviation, so it does not split either.
Why FNV-1a?
It is short, fast and spreads short strings well: for each byte, XOR it into the hash and multiply by the FNV prime. We hash the lower-cased bytes directly, so we never create a lower-case copy of the word.
How do you handle collisions?
Open addressing with linear probing. On a collision we move to the next slot. To confirm a hit we compare the full 64-bit hash first, then the length and the characters, so two different words never get the same id.
What is the complexity of a lookup?
Expected O(L) for a word of length L, because the table is never more than half full and probe sequences stay short. Doubling costs O(V) but happens rarely, so it is amortized O(1) per insert. The theoretical worst case, every word in one cluster, is O(V) per lookup.
Why turn words into integers at all?
After this step, every comparison in the edit distance is one integer comparison instead of a string comparison, and the index can use the id directly as an array position.
Why do you lower-case words and ignore punctuation?
A copied sentence with a changed capital letter or comma is still a copy. The edit rule only counts word edits.
What is (h ^ (h >> 29)) in intern?
The slot is chosen with a bit mask, which keeps only the low bits. Mixing in some high bits first spreads the words more evenly over the table.

Shared part: the whole project on one page (everyone must know this)

Pipeline

  1. Read main_doc.txt and documents/*.txt from the current folder (or --dir). Natural file order.
  2. Split into sentences (generator rule: no split after Mr./St./single capitals, not after a closing quote; empty line ends a sentence).
  3. Words to ids: lower-case, letters and digits, inner ' and - kept; our FNV-1a hash table with linear probing gives each word an int id.
  4. Match: OSA distance on words (insert, delete, replace, swap neighbours), match if distance <= floor(0.3 x longer length). Brute force: every pair, full DP. Efficient: main_doc index, pigeonhole skip, k+1 rarest words, length filter, bag-of-words filter, banded DP.
  5. Output: rate = matched main sentences / all main sentences; documents sorted by rate, ties in file order; up to 5 most similar pairs, edits listed.

Complexity in one line each

  • n main sentences, m documents, s sentences per document, S = m·s, w words per sentence, C characters.
  • Preprocessing: O(C) expected (both versions).
  • Brute force: O(n·S·w²).
  • Efficient: O(C + n·w log w + S·(w log w + n·w) + D·w²); worst case O(n·S·w²) if every pair survives; in practice D = real matches, so about linear.
  • Memory: O(C + V + n·w + m·n).

Numbers everyone should remember

  • Sample: 20/20 found (13 exact, 7 edited), same ranking and rates as expected_output.txt, 0 false matches.
  • 200 documents: 741 ms vs 14 ms (53x) with n = 30; 7.8 s vs 82 ms (96x) with n = 230; whole program 7.96 s vs 0.14 s.
  • Filters on 200 documents: 20 000 sentences, 6 670 skipped at once, 47 440 candidates, 200 DPs = 200 matches (brute: 600 000 DPs).
  • Generated tests: 800/800 (at least 10 words), 798/800 (at least 6 words), 0 false matches.

Questions anyone can get

Which files does it read and how do you run it?
main_doc.txt and documents/*.txt in the folder it is started from. Compile with g++ -std=c++17 -O2 -o plagiarism src/*.cpp, run with ./plagiarism (efficient), brute, compare, benchmark.
Did you use any built-in search?
No find, indexOf or regex in the core. Splitting, tokenizing, hashing and matching are our own code. We use standard containers (vector, sort), which the assignment allows.
Are the brute force and the efficient version really the same?
Same matching rule, and the efficient filters can only reject pairs that cannot match, so the result tables are identical. compare and benchmark check it every run.
What would you improve?
Reading the files is now the slowest part (about 48 ms for 200 documents); it could be done with memory-mapped files or in parallel. We could also make the threshold depend on the sentence length more carefully for very short sentences.
Did you use AI?
Yes, Claude, as written in our AI Use Declaration. We tested everything ourselves and each of us can explain all of the code.
