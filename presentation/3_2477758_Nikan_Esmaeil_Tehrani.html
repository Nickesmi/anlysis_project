3. What to say

The brute force computes 600 000 tables on 200 documents, but only 200 of those pairs are real copies. Our efficient version tries to rule out the other pairs without computing the table, and it never rules out a real match, so its output is exactly the same as the brute force. The compare mode checks that every time.

First we build an inverted index of main_doc only: for every word, the list of main sentences that contain it. main_doc is the small side, so the index is tiny, and then we read every document sentence just once. Our first version indexed all the documents and it was slower.

The key idea is a pigeonhole argument. If a document sentence b matches a main sentence a with at most k edits, every edit removes at most one word of b from a. So if I take any k plus 1 different words of b, at least one of them must be in a. That gives two shortcuts. If k plus 1 words of b do not appear anywhere in main_doc, b cannot match anything and we skip it. Otherwise we only look at main sentences in the lists of the k plus 1 rarest words of b, because rare words have short lists.

Each candidate then goes through two cheap filters: the length filter, because each edit changes the length by at most one, and a bag-of-words bound, the distance is at least the longer length minus the number of common words, which we count by merging two sorted lists. Only what survives gets the banded DP, which only fills the cells with |i minus j| at most k and stops when a whole row is above k.

On 200 documents: 6 670 of 20 000 sentences are skipped right away, 47 440 candidates are checked cheaply, and only 200 DPs are computed, exactly the 200 real matches. In the worst case, if every sentence looked like every other sentence, we would still be O(n times S times w squared) like the brute force, because then every pair really has to be checked. On real text the cost is about linear in the input. Mustafa will show the measured times.

6. Questions you will probably get

Prove that you never lose a match.
Let b match a with d <= k edits. A word of b is missing from a only if all its copies were deleted or replaced, and each of those edits handles one copy; a swap or insert removes nothing. So at most k different words of b are missing from a. Any k+1 different words of b therefore include at least one word that is in a, so a is in one of the posting lists we visit. The length filter and the bag-of-words bound are lower bounds on the distance, and the banded DP is exact when the distance is <= k, so none of them can reject a real match.
Why the rarest words?
Any k+1 words would be correct. The rarest words have the shortest posting lists, so we get the fewest candidates. Words that are not in main_doc at all have empty lists and count first.
Why is k for b bigger than 30% of |b|?
The partner a can be longer than b. If a has |b|+k words it gets k = 0.3(|b|+k), which solves to about 0.43|b|. We need the largest k any partner could get, otherwise we could skip a real match. For |b| = 20 this is 8.
Why index main_doc and not the documents?
main_doc is small, so its index is tiny and fits in cache, and each document sentence is read only once. We tried indexing all documents first; that index has all S sentences and was slower to build.
Why is the banded DP correct?
Every step off the diagonal costs at least one edit, so an alignment with distance <= k never goes more than k cells away from the diagonal. Also, the minimum of a row never gets smaller in the next rows, so once a whole row is above k the final answer is above k too. The self-test compares it with the full DP on 200 000 random pairs.
Why the bag-of-words bound?
To create a word that is not shared you need an insert or a replace, and each edit makes at most one shared word stop being shared, so the distance is at least max(|a|,|b|) minus the common words. Counting common words is an O(w) merge, much cheaper than an O(w·k) table. In our run it removed every non-match before the DP.
What are the stamp arrays?
Instead of clearing a visited array for every sentence, we write the current sentence number into it. A cell counts as visited only if it holds the current number. This makes the distinct-word check O(1) and avoids O(V) clearing.
What is the worst-case complexity of the efficient version?
O(C + n·w log w + S·(w log w + n·w) + D·w²), where D is the number of pairs that reach the DP. If every sentence is almost the same as every other, D = n·S and it is O(n·S·w²) like the brute force; no exact method can avoid that because every pair really must be checked. In practice D is just the real matches.
Why not Rabin-Karp, shingles or LSH?
Hashing whole sentences only finds exact copies. Word bigram shingles need 3k+1 probes because one edit breaks up to 3 bigrams, and lists for common bigrams like "of the" are long. MinHash/LSH is probabilistic and can miss copies. Suffix arrays find exact substrings only.

Shared part: the whole project on one page (everyone must know this)

Pipeline

  1. Read main_doc.txt and documents/*.txt from the current folder (or --dir). Natural file order.
  2. Split into sentences (generator rule: no split after Mr./St./single capitals, not after a closing quote; empty line ends a sentence).
  3. Words to ids: lower-case, letters and digits, inner ' and - kept; our FNV-1a hash table with linear probing gives each word an int id.
  4. Match: OSA distance on words (insert, delete, replace, swap neighbours), match if distance <= floor(0.3 x longer length). Brute force: every pair, full DP. Efficient: main_doc index, pigeonhole skip, k+1 rarest words, length filter, bag-of-words filter, banded DP.
  5. Output: rate = matched main sentences / all main sentences; documents sorted by rate, ties in file order; up to 5 most similar pairs, edits listed.

Complexity in one line each

  • n main sentences, m documents, s sentences per document, S = m·s, w words per sentence, C characters.
  • Preprocessing: O(C) expected (both versions).
  • Brute force: O(n·S·w²).
  • Efficient: O(C + n·w log w + S·(w log w + n·w) + D·w²); worst case O(n·S·w²) if every pair survives; in practice D = real matches, so about linear.
  • Memory: O(C + V + n·w + m·n).

Questions anyone can get

Which files does it read and how do you run it?
main_doc.txt and documents/*.txt in the folder it is started from. Compile with g++ -std=c++17 -O2 -o plagiarism src/*.cpp, run with ./plagiarism (efficient), brute, compare, benchmark.
Did you use any built-in search?
No find, indexOf or regex in the core. Splitting, tokenizing, hashing and matching are our own code. We use standard containers (vector, sort), which the assignment allows.
Are the brute force and the efficient version really the same?
Same matching rule, and the efficient filters can only reject pairs that cannot match, so the result tables are identical. compare and benchmark check it every run.
What would you improve?
Reading the files is now the slowest part (about 48 ms for 200 documents); it could be done with memory-mapped files or in parallel. We could also make the threshold depend on the sentence length more carefully for very short sentences.
Did you use AI?
Yes, Claude, as written in our AI Use Declaration. We tested everything ourselves and each of us can explain all of the code.
