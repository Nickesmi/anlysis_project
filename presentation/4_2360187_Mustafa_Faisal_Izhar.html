3. What to say

We measured both versions with our benchmark mode. It runs both on the first eighth, quarter and so on of the documents, takes the best of five runs, and checks that the results are identical. The sample set has only 20 documents, so we also built a 200-document set from the sample documents with their sentences shuffled, once with the 30-sentence main_doc and once with a 230-sentence main_doc.

Both lines are straight, which matches the analysis: the number of document sentences grows linearly with the number of documents. On 200 documents the brute force needs 741 milliseconds and ours 14, so 53 times faster. With the longer main_doc it is 7.8 seconds against 82 milliseconds, 96 times faster, because the brute force grows with n times S while our version only pays a cheap merge per candidate. For the whole program, including reading the files, it is 0.14 seconds against almost 8.

For accuracy, on the sample set we find all 20 copied sentences with the same ranking and the same percentages as the expected output, and no false matches. With our test generator, 800 out of 800 copied sentences with up to 3 random edits were found, and 798 out of 800 when we also allowed 6-word sentences. The two misses are short sentences where almost half the words changed, more than our 30% rule allows.

The output is one block per document, sorted by the number of matched sentences, with ties in file order, and inside a block the five most similar pairs. Now I will run it on the hidden test set.

6. Questions you will probably get

What exactly did you time?
Only the matching step, and for the efficient version that includes building its index. Reading the files is the same code for both, so we report it separately (about 48 ms for 200 documents). Each number is the best of 5 runs with std::chrono::steady_clock.
Why is the brute force line straight?
Its cost is n times S times w squared. n and w do not change in the experiment and S grows linearly with the number of documents.
Why is the speedup bigger with the longer main_doc?
The brute force does n times S full tables, so it grows 7.7 times when n goes from 30 to 230. In the efficient version more of the main_doc words are known, so more candidates appear, but each candidate costs only an O(w) merge, not an O(w²) table.
The 200 documents are copies. Is that fair?
The sample only has 20 documents, so we repeated them with shuffled sentence order to get realistic sizes. Both versions get exactly the same input, so the comparison is fair. Duplicates only make the efficient version do a bit more work, because copied sentences match in more documents.
How do you rank documents with the same similarity?
We use a stable sort on the matched count, so equal documents keep their file order, document2 before document10.
How do you choose the 5 pairs you print?
By relative distance, distance divided by the longer sentence length, smallest first. Exact copies come first. We compare fractions by cross-multiplying, so no floating point is needed.
How do you know the two versions agree?
compare and benchmark check the full result tables for equality: every document, every main sentence, the chosen pair and its distance. compare exits with an error if they differ. It never happened in any test.
What do you do if the hidden test set gives a different result?
We report what we get. The percentages depend on the sentence count, so if a sentence is split differently from the generator the numbers move a little; we explain that in the report.

Shared part: the whole project on one page (everyone must know this)

Pipeline

  1. Read main_doc.txt and documents/*.txt from the current folder (or --dir). Natural file order.
  2. Split into sentences (generator rule: no split after Mr./St./single capitals, not after a closing quote; empty line ends a sentence).
  3. Words to ids: lower-case, letters and digits, inner ' and - kept; our FNV-1a hash table with linear probing gives each word an int id.
  4. Match: OSA distance on words (insert, delete, replace, swap neighbours), match if distance <= floor(0.3 x longer length). Brute force: every pair, full DP. Efficient: main_doc index, pigeonhole skip, k+1 rarest words, length filter, bag-of-words filter, banded DP.
  5. Output: rate = matched main sentences / all main sentences; documents sorted by rate, ties in file order; up to 5 most similar pairs, edits listed.

Complexity in one line each

  • n main sentences, m documents, s sentences per document, S = m·s, w words per sentence, C characters.
  • Preprocessing: O(C) expected (both versions).
  • Brute force: O(n·S·w²).
  • Efficient: O(C + n·w log w + S·(w log w + n·w) + D·w²); worst case O(n·S·w²) if every pair survives; in practice D = real matches, so about linear.
  • Memory: O(C + V + n·w + m·n).

Numbers everyone should remember

  • Sample: 20/20 found (13 exact, 7 edited), same ranking and rates as expected_output.txt, 0 false matches.
  • 200 documents: 741 ms vs 14 ms (53x) with n = 30; 7.8 s vs 82 ms (96x) with n = 230; whole program 7.96 s vs 0.14 s.
  • Filters on 200 documents: 20 000 sentences, 6 670 skipped at once, 47 440 candidates, 200 DPs = 200 matches (brute: 600 000 DPs).
  • Generated tests: 800/800 (at least 10 words), 798/800 (at least 6 words), 0 false matches.

Questions anyone can get

Which files does it read and how do you run it?
main_doc.txt and documents/*.txt in the folder it is started from. Compile with g++ -std=c++17 -O2 -o plagiarism src/*.cpp, run with ./plagiarism (efficient), brute, compare, benchmark.
Did you use any built-in search?
No find, indexOf or regex in the core. Splitting, tokenizing, hashing and matching are our own code. We use standard containers (vector, sort), which the assignment allows.
Are the brute force and the efficient version really the same?
Same matching rule, and the efficient filters can only reject pairs that cannot match, so the result tables are identical. compare and benchmark check it every run.
What would you improve?
Reading the files is now the slowest part (about 48 ms for 200 documents); it could be done with memory-mapped files or in parallel. We could also make the threshold depend on the sentence length more carefully for very short sentences.
Did you use AI?
Yes, Claude, as written in our AI Use Declaration. We tested everything ourselves and each of us can explain all of the code.
